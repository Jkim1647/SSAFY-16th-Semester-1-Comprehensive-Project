# 알고리즘 선택 근거

EnjoyTrip EV 에 넣은 알고리즘 9개를 **왜 이것으로 골랐는지**, **다른 방법은 왜 안 썼는지**, **언제 바꿔야 하는지**를 정리한 문서입니다.
BackEnd 관통이나 발표에서 "이거 왜 이렇게 했어요?"라는 질문에 팀원 누구나 같은 근거로 답할 수 있게 만들었습니다.
측정값은 모두 [README 성능 측정](../ALGORITHM-PLAN.md#성능-측정)과 같은 값입니다(Java 1.8.0_192, Windows 11).

## 모든 결정에 깔린 전제

| 전제 | 내용 | 결정에 미친 영향 |
|---|---|---|

## #1 방문 순서 최적화 — Held-Karp DP + 최근접 이웃·2-opt

**문제와 조건**: 출발지 + 관광지 n곳을 한 번씩 들르는 가장 짧은 순서(TSP). 하루 여행은 보통 10곳 안팎, 많아도 수십 곳.

**검토한 후보**

| 후보 | 시간 | 결과 |
|---|---|---|
| 완전탐색(순열) | O(n!) | n=10 에서 66ms, n=12 부터 측정 불가(12! ≈ 4.8억) |
| **Held-Karp 비트마스크 DP** | O(n²·2ⁿ), 메모리 O(n·2ⁿ) | n=14 에서 4ms, 최적해 보장 |
| **최근접 이웃 + 2-opt** | O(n²·반복) | 500곳 18ms, 최적 대비 +0.3~1.0% |
| 유전 알고리즘·담금질 | 반복 횟수에 따라 | 결과가 실행마다 달라 검증·설명이 어려움 |
| Google OR-Tools 등 솔버 | - | 외부 라이브러리 의존 (core 모듈 원칙과 충돌) |

**선택과 근거**: 실제 사용 범위(≤15곳)에서는 Held-Karp 로 **항상 최적해**를 수 ms 에 줍니다. n 이 1 늘 때마다 메모리가 2배 넘게 늘어(n=16 12MB, n=20 약 240MB) 15곳을 기준으로 근사 해법으로 넘깁니다. 2-opt 는 최근접 이웃만 쓸 때의 7~15% 손해를 1% 안팎으로 줄입니다.

**버린 대안**: 완전탐색은 n=12 부터 불가능. 메타휴리스틱은 같은 입력에 다른 답이 나와 "왜 이 순서냐"를 설명하기 어렵고, 이 규모에서는 정확해가 이미 빠릅니다.

**바꿀 조건**: 관광지 영업시간, 숙소 체크인 시각, "마지막은 숙소" 같은 **제약**이 생기면 단순 TSP 가 아니므로 제약을 다루는 솔버나 DP 상태 확장이 필요합니다.

## #2 충전소 경유 경로 — Dijkstra (배열 구현) + 회랑·급속 필터

**문제와 조건**: 출발지→도착지 사이에 배터리가 최소 잔량(10%) 아래로 떨어지지 않도록 충전소를 끼워 넣어, 주행 + 충전 시간을 최소화. 충전소 8,072곳.

**핵심 모델링 결정**: "충전소에서는 항상 목표 잔량(80%)까지 충전한다"는 정책을 두면 충전소를 떠나는 잔량이 경로와 무관하게 같아집니다. 그래서 간선 비용이 (u, v) 만으로 정해지고 음수가 없어, **잔량을 상태에 넣지 않고도 Dijkstra 가 최적**입니다.

**검토한 후보**

| 후보 | 판단 |
|---|---|
| **배열 Dijkstra O(V²)** | 모든 충전소 쌍이 연결될 수 있는 조밀 그래프라 힙보다 유리 |
| 힙 Dijkstra O(E log V) | E ≈ V² 이라 O(V² log V) 로 오히려 느림 |
| A* | 직선 주행 시간을 휴리스틱으로 쓰면 최적성 유지 가능. 꺼내는 정점 수를 줄일 수 있지만 **측정하지 않음** — 개선 후보 |
| 잔량을 상태로 둔 탐색 (위치, 잔량) | 목표 충전량을 자유롭게 정할 수 있어 더 정확하지만 상태 수가 수십 배 |
| 고정 규칙 (주행 가능 거리 70% 에서 충전, 3회차 방식) | 충전소 위치·출력을 보지 않아 불필요한 충전·잔량 부족 발생 |

**선택과 근거**: 모델링으로 단순한 Dijkstra 를 쓸 수 있게 만든 것이 핵심입니다. 무작위 300건에서 완전탐색(DFS)과 결과가 모두 같았습니다. 다만 8,072곳 전체로 돌리면 쌍당 약 2.3초라, 경로에서 크게 벗어난 충전소(회랑 필터)와 완속 충전소(급속 필터)를 빼 **중앙값 17ms, 최악 264ms** 로 줄였습니다.

**알아야 할 한계**: 필터는 "갈 수 있는가"는 보장하지만(실패하면 범위를 넓혀 다시 찾음) **전체 충전소 기준 최소 시간은 보장하지 않습니다**. 실데이터 179쌍에서는 전체 탐색과 모두 같았고, 테스트에 다를 수 있는 예시를 넣어 두었습니다.

**바꿀 조건**: 여행 전체를 한 번에 최적화해야 하거나(앞 구간에서 더 충전해야 다음 구간이 가능한 경우), 충전량을 80% 외로 바꾸고 싶으면 (위치, 잔량 구간) 상태 공간 탐색. 실시간 충전기 상태(고장·사용 중)는 후보에서 빼는 방식으로 반영.

## #3 비밀번호 저장 — PBKDF2 직접 구현 + salt + pepper + 키 스트레칭

**문제와 조건**: 회원 비밀번호를 평문 없이 저장. DB 가 유출돼도 원래 비밀번호를 알아내기 어렵게.

**검토한 후보**

| 후보 | 판단 |
|---|---|
| SHA-256 한 번 | 너무 빨라(1초에 수십억 번) 무차별 대입에 취약, 레인보우 테이블에도 약함 |
| **PBKDF2-HMAC-SHA256** | 반복으로 비용을 키움. **JDK 에 HMAC 이 있어 외부 라이브러리 없이 구현** 가능 |
| bcrypt | 널리 쓰이지만 JDK 에 없음 |
| Argon2id | 메모리를 많이 써 GPU 병렬 공격에 가장 강함. **OWASP 1순위 권고**. JDK 에 없음 |

**선택과 근거**: 수업 취지(원리를 알고 쓰기)와 core 모듈 원칙(의존성 없음)을 둘 다 만족하는 것이 PBKDF2 입니다. 직접 구현했기 때문에 **RFC 7914 테스트 벡터와 JDK 구현 결과로 정확성을 검증**했습니다. 반복 횟수는 OWASP 권고값 600,000회(해시 1회 Java 8 약 0.74초, JDK 25 약 0.2초)이고, 저장 형식에 반복 횟수를 넣어 나중에 기준을 올릴 수 있습니다.

**바꿀 조건**: 운영 서비스라면 Spring Security 의 `Argon2PasswordEncoder` 로 바꾸는 것을 권장합니다. 저장 문자열 앞에 알고리즘 이름(`pbkdf2_sha256$…`)이 있어 두 방식이 섞여 있어도 구분할 수 있습니다. 로그인 API 에는 IP·계정별 요청 제한을 함께 둡니다.

## #4 검색창 자동완성 — Trie + 노드별 Top-K + 초성 Trie

**문제와 조건**: 글자를 칠 때마다(초당 여러 번) 후보 10개 이하를 보여 줌. "ㄷㅇ"처럼 초성만 쳐도 찾아야 함.

**검토한 후보**

| 후보 | 판단 |
|---|---|
| 매번 전체 검사 + 정렬 | 검색어 1개 11µs. 지금 규모에서도 가능하지만 데이터에 비례해 느려짐 |
| DB `LIKE '담%'` | 앞부분 일치는 인덱스를 탈 수 있지만, 초성 검색·"오동도로 한려해상국립공원(오동도) 찾기"는 별도 컬럼·처리가 필요 |
| **Trie + 노드별 Top-K** | 조회 O(P+K), 검색어 1개 0.4µs. 초성 Trie 를 하나 더 두면 초성 검색 |

**선택과 근거**: 자동완성은 요청이 가장 잦은 기능이라 조회를 최대한 싸게 만들고, 비용은 서버 시작 시 한 번(만들기 32ms, 노드 14,577개)으로 옮겼습니다. 각 노드에 "이 접두어의 점수 상위 K개"를 미리 저장해 짧은 접두어("광")에서도 하위 트리를 돌지 않습니다. 점수는 주변 급속 충전소 수로 정해 EV 여행자에게 맞췄습니다.

**바꿀 조건**: 관광지가 전국 수십만 건이 되거나 실시간으로 자주 바뀌면, 검색엔진(Elasticsearch 의 completion suggester 등)으로 옮기는 것을 검토합니다.

## #5 키워드 검색 — KMP

**문제와 조건**: 이름·주소 안 어디에든 있는 키워드("국립공원")를 찾고, 찾은 위치를 하이라이트.

**검토한 후보와 측정**

| 입력 | KMP | 단순 비교 | `String.indexOf` 반복 |
|---|---:|---:|---:|
| 최악 입력 (a×100만 에서 a×1000+b) | **9.8ms** | 635ms | 467ms |
| 실제 관광지 이름+주소 | 0.74ms | 0.68ms | **0.02ms** |

**선택과 근거**: KMP 의 장점은 **최악의 경우 O(N+M) 보장**입니다. 실제 데이터처럼 어긋남이 빨리 나는 입력에서는 JDK `indexOf`(내부 최적화)가 더 빠르다는 것도 측정으로 확인했습니다. 수업 범위(패턴 매칭)를 서비스에 접목하고, 모든 등장 위치를 돌려줘 하이라이트에 바로 쓰려고 KMP 를 썼습니다.

**바꿀 조건**: 게시판 본문처럼 검색 대상이 커지면 매번 전체를 훑는 방식 자체가 맞지 않습니다. 이때는 MySQL FULLTEXT(한글은 ngram parser)나 검색엔진의 역색인으로 옮깁니다.

## #6 목록 정렬 — TimSort 직접 구현

**문제와 조건**: 관광지 목록을 "가까운 순 / 충전소 많은 순 / 이름순"으로, 기준 값이 같으면 이름순이 유지되게.

**검토한 후보**: JDK `List.sort`(내부가 TimSort), DB `ORDER BY`, 직접 구현.

**선택과 근거 — 솔직한 답**: 결과만 보면 **JDK `List.sort` 로 충분**합니다. 직접 구현한 이유는 수업(정렬, TimSort 강의)과 연결해 원리를 익히고, 그것이 맞는지 **JDK 결과와 크기 14종 × 패턴 6종에서 비교해 검증**하기 위해서입니다. 서비스에서 쓰는 성질은 **안정 정렬**입니다: 이름순으로 한 번 정렬한 뒤 거리로 다시 정렬하면, 거리가 같은 곳은 이름순이 유지되어 비교 함수를 복잡하게 만들지 않아도 됩니다. 정렬된 입력에서 비교 n−1번(단순 병합 정렬의 1/8)인 것도 확인했습니다.

**알아야 할 한계**: galloping 모드를 생략해, 같은 값이 많은 입력에서 JDK 보다 비교가 약 2배 많습니다.

**바꿀 조건**: 운영 코드에서는 JDK 정렬을 쓰거나, 데이터가 DB 에 있으면 `ORDER BY` + 인덱스로 DB 가 정렬하게 합니다.

## #7 관광지 추천 — 코사인 유사도 + 격자 인덱스 + Top-K 힙

**문제와 조건**: 사용자가 고른 분류·찜한 곳과 비슷하고, 가깝고, 충전하기 좋은 관광지 10곳. 아직 회원 사용 기록이 없음.

**검토한 후보**

| 부분 | 후보 | 판단 |
|---|---|---|
| 취향 | 협업 필터링 | "비슷한 사용자"가 필요한데 **사용 기록이 아직 없음** (콜드 스타트) |
| 취향 | **콘텐츠 기반 + 코사인 유사도** | 관광지 분류 코드만으로 바로 가능. 찜을 많이 한 사람과 적게 한 사람을 공평하게 비교(크기로 나눔) |
| 주변 충전소 수 | 전체 비교 | 1,504 × 2,119 쌍, 880ms |
| 주변 충전소 수 | **격자 인덱스 (2km 칸)** | 21.5ms(약 41배). 고정 반경 질의에 구현이 단순 |
| 주변 충전소 수 | KD-Tree | 분포가 고르지 않을 때 유리하지만 구현·설명이 더 복잡. 이 규모·반경에서는 격자로 충분 |
| 주변 충전소 수 | DB 공간 인덱스 (MySQL SPATIAL) | DB 가 생기면 좋은 선택지. 지금은 DB 가 없음 |
| 상위 K개 | 전체 정렬 O(N log N) vs **최소 힙 O(N log K)** | 지금 규모에선 1.72ms vs 2.10ms 로 차이가 작지만 데이터가 늘수록 유리 |

**선택과 근거**: 사용 기록 없이 시작할 수 있는 방법을 고르고, "무엇을 중요하게 볼지(취향/가까움/충전)"를 가중치로 사용자가 정하게 했습니다. 세부 점수를 함께 돌려줘 "왜 추천했는지"를 화면에 보여 줄 수 있습니다.

**바꿀 조건**: 찜·방문 기록이 쌓이면 협업 필터링을 섞습니다. 관광지가 DB 에 들어가면 주변 충전소 수는 DB 공간 인덱스로 계산해 저장해 둘 수 있습니다.

## #8 도로 거리 — 카카오모빌리티 API + 캐시 + 실패 시 대체

**문제와 조건**: 하버사인 직선거리는 바다·산을 가로지르는 거리라 실제와 다름(강사님이 지적한 한계).

**측정**: 시연 관광지 55쌍에서 도로/직선 비율 중앙값 **1.42**, 최대 **3.07**(땅끝마을 ↔ 진도 운림산방). 기존 근사(× 1.3)의 평균 오차 **11.3%**. 도로 거리로 정한 방문 순서가 직선 근사로 정한 순서보다 10.5km 짧았습니다.

**검토한 후보**

| 후보 | 판단 |
|---|---|
| 직선 × 1.3 | 빠르고 무료지만 섬·해안에서 크게 틀림 |
| 도로망 데이터로 직접 최단 경로 | 전국 도로망 데이터·교통 반영이 필요해 범위 밖 |
| **길찾기 API (카카오모빌리티)** | 정확. 유료 API 라 일일 무료 사용량 안에서 써야 함(한도는 카카오 디벨로퍼스 콘솔에서 확인) |

**선택과 근거**: 알고리즘 코드를 바꾸지 않도록 거리 계산을 `DistanceCalculator` 인터페이스로 분리(전략 패턴)하고, API 구현을 끼워 넣었습니다. 같은 두 지점은 다시 묻지 않게 캐시해 n곳의 거리 행렬은 n(n−1)/2번만 호출하고, API 실패 시 직선 근사로 대신하되 대체 횟수를 기록합니다.

**바꿀 조건**: 사용자가 늘면 호출량이 한도를 넘으므로, 계산한 도로 거리를 DB 에 저장해 재사용합니다. 충전 경로(#2)는 후보가 수백 곳이라 쌍마다 호출할 수 없어 계속 직선 근사를 씁니다.

## #9 오타 허용 검색 — 자모 단위 편집 거리 DP + 3-gram 필터

**문제와 조건**: KMP 는 한 글자만 틀려도("국림공원") 0건. 한/영 전환을 잊고 친 "ekadid"도 못 찾음.

**검토한 후보**

| 후보 | 판단 |
|---|---|
| 글자 단위 편집 거리 | '림'과 '립'이 그냥 다른 글자라 받침 하나 틀림이 글자 하나 틀림과 같게 계산됨 |
| **자모(키 입력) 단위 편집 거리** | 받침 하나 틀림 = 거리 1. 실제 키보드 오타에 가까움 |
| Elasticsearch fuzzy 검색 | 같은 원리(편집 거리 + 역색인)를 제공하지만 별도 서버 운영이 필요 |
| BK-Tree | 단어 단위 전체 일치에 강함. 이름 **일부**만 친 검색어(부분 문자열)에는 맞지 않음 |

**선택과 근거**: DP 로 "검색어와 가장 가까운 이름의 부분"을 찾고(첫 행 0 초기화), 그 구간을 하이라이트에 씁니다. 자모 3-gram 역색인으로 후보를 줄이되, **정답을 놓치지 않는 하한 조건(q-gram 보조정리)** 만 써서 결과가 전체 비교와 같다는 것을 테스트로 확인했습니다. 오타 1개 검색어 1,000개에서 **KMP 0% → 98.5%** 를 찾았습니다.

**알아야 할 한계**: 검색어가 짧으면 필터가 거의 걸러내지 못합니다(1,504 → 평균 1,038곳). 지금 규모에서는 1회 2ms 안팎이라 문제없지만, 데이터가 커지면 필터를 강화하거나 검색엔진으로 옮깁니다. 검색어 길이는 30자로 제한해 과도한 요청을 막습니다.

## 공통 질문: DB 가 생기면 이 알고리즘들은 어디서 돌아야 하나?

| 기능 | 서버 메모리(지금 방식) | DB 로 옮길 수 있는 부분 |
|---|---|---|
| #1 #2 경로 | 요청마다 계산 (입력이 사용자마다 다름) | 관광지·충전소 조회만 DB |
| #4 #5 #9 검색 | 시작 시 Trie·역색인을 만들어 메모리에 둠 | 데이터가 커지면 FULLTEXT·검색엔진 |
| #6 정렬 | 메모리 정렬 | `ORDER BY` + 인덱스 |
| #7 추천 | 메모리 계산 | 주변 충전소 수는 SPATIAL 인덱스로 미리 계산해 컬럼에 저장 |

지금 데이터는 수 MB 라 서버 메모리에 두는 것이 가장 빠르고 단순합니다. 그래서 `backend` 는 DAO 인터페이스 뒤에서 데이터를 읽고, 서비스가 시작할 때 자료구조를 만들도록 나눠 두었습니다. DB 로 옮겨도 서비스·컨트롤러는 그대로이고, 데이터가 바뀌면 자료구조를 새로 만들어 참조를 바꿔 끼우면 됩니다.

## 예상 질문과 답변

**Q1. 라이브러리나 DB 기능이 있는데 왜 직접 구현했나요?**
수업 목표가 "알고리즘을 이해하고 서비스에 접목해 직접 구현"이기 때문입니다. 대신 직접 구현한 것은 모두 완전탐색이나 표준 구현(JDK, RFC 테스트 벡터)과 비교해 결과가 같다는 것을 확인했습니다. 운영에서 표준 구현으로 바꿔야 하는 것(정렬 → JDK, 비밀번호 → Argon2)은 문서에 명시했습니다.

**Q2. 방문 순서에 왜 15곳에서 방법을 바꾸나요?**
Held-Karp 는 n 이 1 늘 때마다 메모리가 2배 넘게 늘어납니다. n=16 이 12MB, n=20 이면 약 240MB 라 요청마다 쓰기에는 부담입니다. 15곳 이하는 수 ms 에 최적해, 그 이상은 2-opt 로 최적 대비 1% 안팎입니다.

**Q3. Dijkstra 는 상태(배터리 잔량)가 있는 문제에 바로 못 쓰지 않나요?**
그래서 "충전소에서는 항상 80%까지 충전"이라는 정책을 두었습니다. 충전소를 떠나는 잔량이 항상 같으니 간선 비용이 (출발, 도착)만으로 정해지고, 일반 Dijkstra 로 최적해가 됩니다. 이 정책 자체가 단순화라는 점이 한계입니다.

**Q4. 충전 경로가 항상 최적인가요?**
필터 안의 후보 충전소 중에서는 최적이지만, 필터 밖까지 포함한 전체 기준 최적은 보장하지 않습니다. 실데이터 179쌍에서는 전체 탐색과 모두 같았습니다. 전체 최적이 꼭 필요하면 필터를 끌 수 있지만 쌍당 수 초가 걸립니다.

**Q5. 왜 A* 를 쓰지 않았나요?**
직선 주행 시간을 휴리스틱으로 쓰면 A* 도 최적을 유지할 수 있어 좋은 개선 후보입니다. 이번에는 정확성을 검증하기 쉬운 Dijkstra 와 후보 줄이기(필터)로 목표 시간을 맞췄고, A* 는 측정하지 않았습니다.

**Q6. 자동완성을 DB `LIKE` 로 하면 안 되나요?**
앞부분 일치는 `LIKE '담%'` 로 가능하지만, 초성 검색("ㄷㅇ")과 이름 중간 단어("오동도")는 따로 처리해야 하고, 글자를 칠 때마다 DB 를 부르게 됩니다. 데이터가 작아 Trie 를 메모리에 두면 0.4µs 에 끝납니다.

**Q7. KMP 가 `indexOf` 보다 느린 경우가 있던데요?**
맞습니다. 실제 주소 데이터에서는 `indexOf` 가 더 빨랐습니다. KMP 의 가치는 최악의 경우(앞부분이 계속 맞다가 어긋나는 입력)에도 O(N+M) 을 보장하는 것이고, 측정에서 최악 입력 65배 차이로 확인했습니다.

**Q8. 추천에 왜 협업 필터링이 아닌가요?**
협업 필터링은 사용자들의 찜·방문 기록이 필요한데 지금은 기록이 없습니다(콜드 스타트). 관광지 분류만으로 가능한 콘텐츠 기반 추천으로 시작하고, 기록이 쌓이면 섞을 계획입니다.

**Q9. 격자 인덱스 대신 KD-Tree 는요?**
KD-Tree 는 데이터 분포가 고르지 않을 때 유리합니다. 이번 질의는 "반경 3km 안 개수"처럼 반경이 고정되어 있고 규모가 작아, 구현과 설명이 단순한 격자로 충분했습니다(전체 비교 대비 약 41배). DB 가 생기면 MySQL 공간 인덱스가 더 나은 선택일 수 있습니다.

**Q10. PBKDF2 가 Argon2 보다 약하다면서 왜 썼나요?**
Argon2 는 JDK 에 없어 외부 라이브러리가 필요하고, 이번에는 원리(salt, pepper, 키 스트레칭)를 직접 구현해 검증하는 것이 목적이었습니다. 운영에서는 Spring Security 의 Argon2 인코더로 바꾸는 것을 권장하며, 저장 형식에 알고리즘 이름이 있어 섞여 있어도 구분됩니다.

**Q11. 오타 검색에서 필터 효과가 작은데 의미가 있나요?**
짧은 검색어는 허용 오타 대비 3-gram 이 적어 필터가 거의 걸러내지 못합니다(측정에서 평균 31% 감소). 대신 필터가 정답을 놓치지 않는다는 것을 테스트로 보장했고, 검색어가 길거나 데이터가 커질수록 효과가 커집니다. 지금 규모에서는 필터 없이도 1회 2ms 안팎입니다.

**Q12. 도로 거리 API 비용은요?**
같은 두 지점은 캐시해 다시 묻지 않고, 관광지 n곳에 n(n−1)/2번만 호출합니다. 사용자가 늘면 계산한 거리를 DB 에 저장해 재사용해야 합니다. 충전 경로처럼 후보가 수백 곳인 계산에는 쓰지 않고 직선 근사를 씁니다.
